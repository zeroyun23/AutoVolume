## 1. 背景与目标

### 1.1 要解决的问题

Windows 没有 Android 式的音频焦点：同一输出设备上的所有音频默认硬混音，网页视频开始播放时，后台音乐不会被压低，也不会暂停。用户的实际痛点是「看视频时音乐还在响，手动暂停再恢复很烦」。

### 1.2 典型场景

- Edge 看网页视频 / B 站 → 暂停音乐、音量切到视频方案；
- 关闭标签/浏览器 → 恢复音乐、音量切回音乐方案；
- VLC、PotPlayer、Win11 媒体播放器、PowerToys 速览预览同理；
- 插拔耳机、切输出设备、休眠唤醒不能误判；
- 用户手动调过音量后，下次要记住。

### 1.3 明确不做（用户已否决，别偷偷加回来）

| 不做 | 原因 |
|---|---|
| 媒体键（VK_MEDIA_*） | 发给“当前会话”，视频一开就打到浏览器身上 |
| 静音兜底代替暂停 | 音乐会继续走，恢复时对不上进度 |
| 按应用调音量（per-app volume）替代主音量 | 用户要的是“整体听感切换”，且部分应用不受控 |
| 方案优先级 / 互斥规则 | 方案只有 members + 每设备音量，保持模型简单 |
| 常驻服务 / 驱动 | 托盘应用足够，避免安装与权限复杂度 |

> 0.3.7 加的「会话静音」不是静音兜底：它只在**暂停成功后**把该应用会话静音 1.5 s，用来掐掉播放器自己的淡出尾音；音乐已经处于 Paused 状态，不是用静音假装暂停。

## 4. 核心实现

### 4.1 分层

```
Core（纯逻辑） ← Runtime（IO/时序） ← App（WPF）
                     ↑
                  Audio（COM/WinRT）
```

依赖单向，Core 不知道 Audio 存在。

### 4.2 一次切换的真实数据流

```
每 50 ms（活跃）/ 500 ms（空闲）
  ├─ WasapiSessionProbe：枚举会话，取白名单 exe 的 state/peak
  ├─ SmtcService.GetSnapshotAsync()：200 ms 缓存
  ▼
SnapshotBuilder：聚合同名 exe → 合并 SMTC（AUMID 匹配/别名）→ PID 验活 → 窗口判据
  ▼
Engine.Tick(snapshot)：纯函数，输出 PausePlayers / ResumePlayers / SetVolume
  ▼
Runtime.ExecuteAsync：
  Pause → TryPauseAsync → 轮询确认（≤300 ms）→ 会话静音（保持 1.5 s）→ 等 80 ms
  Volume → VolumeFader（fadeMs<150 走单次写入 + 350 ms 校验）
  Resume → 先降音量 → 解除静音 → TryPlayAsync
  学习 → 写配置（渐变结束后 1.2 s 内不学习）
  Journal → 有暂停者时写，恢复后清空
```

**实测时间线（0.3.12，fadeMs=100）**：

```
01:25:15.553  cloudmusic.exe 暂停确认 120ms
01:25:16.004  音量 → video = 0.140     ← 451 ms 后
01:25:16.008  状态 → SUSPENDED
```

### 4.3 状态机

`Idle → Suspended → PendingRestore → Restoring → Idle`

关键字段（`Engine.cs`）：

| 字段 | 用途 |
|---|---|
| `_soundingSince` | 每个源首次有声时间（ConfirmMs） |
| `_lastSoundingAt` | 最近一次瞬时峰值（SoundingHoldMs） |
| `_episodeSources` | 本轮响过的源，用于关闭判定与音量归属 |
| `_pausedByUs` | 我们暂停了谁，恢复责任的唯一依据 |
| `_pauseFailedAt` | 暂停失败冷却 2 s |
| `_smtcGoneSince` | SMTC 消失确认 500 ms |
| `_pendingRestoreSince` | 恢复等待起点 |
| `_silentSince` | 宽松模式全静音起点 |
| `_suppressUntil` | 抑制截止 |
| `_userOverride` | 用户接管，本周期不再暂停 |
| `_lastScheme` | 当前音量归属，防重复写 |

### 4.4 Audio 层

| 类 | 职责 | 要点 |
|---|---|---|
| `WasapiSessionProbe` | 枚举 render 会话、读 state/peak | 全量 3.46 ms；白名单缓存读 0.11 ms；拓扑 1 s 重建 |
| `SmtcService` | SMTC 读取 + 暂停/播放 | `MatchesExe` 先做 AUMID/进程名互含，再查别名表 |
| `EndpointVolumeController` | 主音量 scalar | `SetMasterVolumeLevelScalar`；**不 SetMute**；设备切换 `Rebind()` |
| `SessionVolumeController` | 单应用会话静音 | `ISimpleAudioVolume`；只恢复自己改过的静音；`MuteTemporarily` 1.5 s |
| `DeviceWatcher` | 默认设备变化 | 回调只置标志 |
| `WindowProbe` | 是否有可见窗口 | 速览关闭判据 |
| `EndpointSwitcher` | 切默认输出设备 | **未使用**，预留 |

**AUMID 别名表**（`SmtcService.AumidAliases`）：

```csharp
("Microsoft.Media.Player", "ZuneMusic")   // Win11 媒体播放器：exe 与 AUMID 完全对不上
```

### 4.5 Runtime 层（改音量逻辑前必读）

`VolumeFader.FadeToAsync(target, durationMs, tolerance)`：

| 分支 | 行为 |
|---|---|
| `durationMs < 150` | **单次写入** target → 等 350 ms 回读 → 偏差 >0.01 再写一次 → 等 250 ms 回读 |
| `durationMs ≥ 150` | 8 步 smoothstep，**步进 ≥25 ms**；结束等 300 ms 校验，最多补写 3 次 |
| 中止判定 | 回读**跑出 `[start, target] ± tolerance`** 且连续两次 → 判定用户抢音量；区间内的滞后不算 |
| 失败处理 | 写 `LastAbort` / `LastDetail`，**不调用 LearnVolume** |

> 为什么这么复杂：这个音频端点在密集写入后，`GetMasterVolumeLevelScalar` 会返回**排队旧值**（实测 0.08/0.12/0.14 乱跳）。拿回读当“用户是否干预”的依据会误判，进而把中间值学进方案。详见 `M3-报告.md` §16–17。

`AutoVolumeRuntime` 重要行为：

- 暂停成功后 `_sessions.MuteTemporarily(exe, 1500)`，settle 取 `min(pauseSettleMs, 80)`；
- 每 tick `UnmuteExcept(_engine.PausedByUs)`，让权/手动恢复不会把应用按在静音；
- 恢复顺序：`SetVolume` → `Unmute` → `TryPlay`；
- 学习静默窗 `max(userWindowMs, 1200)`；
- 自愈每个进程只跑一次，全程 `await` + 3 s 超时。

### 4.6 App 层

`App.xaml.cs`（参数、单实例、首启、退出恢复、崩溃日志）、`TrayIcon.cs`、`SettingsWindow`（三页签，保存不关窗）、`Autostart.cs`、`LogFile.cs`、`AppIcon.cs`。

设置页保存时**用 UI 状态重建整份配置**——新增字段必须在 `OnSave` 显式赋值，否则会被清空。

### 4.7 判定规则（摘要）

| 规则 | 当前实现 |
|---|---|
| 有声 | peak > 0.003；连续 `confirmMs`，或 peak ≥0.02 且持续 600 ms；峰值归零后 `soundingHoldMs` 内仍算在响 |
| 关闭（有 SMTC） | 会话消失持续 500 ms |
| 关闭（无 SMTC） | 进程退出（Inactive 只代表暂停） |
| 关闭（速览） | `closeSignal=window`，无可见窗口 |
| 严格模式 | 全部源关闭 + `restoreMs` |
| 宽松模式 | 全部静音 + `restoreMs` |
| 音量归属 | 挂起期间按本轮未关闭的源；恢复时忽略源，按播放器/默认方案 |
| 抑制 | 设备变化 2 s、休眠/时钟跳变 2 s、枚举异常 10 s |
| 让权 | 被暂停的播放器自行恢复播放 → 本周期不再暂停 |

### 4.8 与规格的偏差记录（`交接文档.md`）

| 规格 | 实现 | 原因 |
|---|---|---|
| 渐变默认 300 ms | 用户配置 100 ms，代码对 <150 ms 走单次写入 | 用户要求更快；分步写入在该端点不可靠 |
| 暂停后等 300 ms 再升音量 | 会话静音 + 等 80 ms | 尾音不再靠等待，靠静音掐掉 |
| 无静音 | 暂停后临时会话静音 1.5 s，失败不用 | 掐尾音，不是兜底 |
| 恢复延迟 3 s | 本地配置 2 s | 用户偏好 |
| 关闭判定 | 增加 `closeSignal=window`、UWP AUMID 别名 | 速览与媒体播放器的实际行为 |

## 5. 关键决策与原因

| 决策 | 原因 |
|---|---|
| 只调系统主音量 | 用户要整体听感；per-app 音量对部分应用无效 |
| 检测用 WASAPI 峰值 | 唯一能覆盖“任意应用是否真的在出声”的通用信号 |
| 控制优先 SMTC | 系统级、不需要窗口焦点；媒体键会打错目标 |
| 失败不静音兜底 | 音乐进度会继续，恢复体验差（D11） |
| 严格模式默认 | 暂停视频不等于关闭，用户明确要求关了才恢复 |
| 自包含单文件 | 目标机器不装 .NET；不裁剪（SMTC 会失效）、不压缩（内存 14→90 MB） |
| Core 纯逻辑 | 状态机可测、可复现，不被 COM/时钟污染 |
| 会话静音掐尾音 | 播放器暂停自带 1 s 淡出，等待不可靠；静音是唯一能立刻掐断的手段 |
| 回读只做校验、不做中止依据 | 该端点回读排队滞后，拿它判断用户操作会误伤 |
| UWP 用 AUMID 别名 | 媒体播放器 exe 与包名毫无关系，必须显式映射 |

## 6. 已知问题与风险

### 6.1 退出期 CLR 卸载异常（0.3.13 已修复）

**症状**：`用户退出` 之后（实测 15 ms – 33 s），进程以未处理异常终止，事件日志 `.NET Runtime 1026`：

```
System.DllNotFoundException: Dll was not found.
   at __std_type_info_destroy_list(__type_info_node*)
   at __scrt_uninitialize_type_info()
   at _app_exit_callback()
   at <CrtImplementationDetails>.ModuleUninitializer.SingletonDomainUnload(Object source, EventArgs arguments)
```

**根因（已实测确认，不是 COM/WinRT 释放顺序）**：

1. WPF 的 `DirectWriteForwarder.dll` / `System.Printing.dll` 是 **C++/CLI 混合模式**程序集，在 `ProcessExit` 阶段执行 CRT 反初始化（`__scrt_uninitialize_type_info`）。事件栈省略的最后一帧是 `System.AppContext.OnProcessExit()`。
2. 该反初始化需要 `vcruntime140_cor3.dll`，而**正常运行时这个 DLL 从未被加载**（`GetModuleHandle` 返回 0）——它只在退出时**按名延迟加载**。
3. 单文件自解压模式下它只存在于 `%TEMP%\.net\AutoVolume\<hash>\`（7.9 MB，5 个 WPF 原生库）。退出时该目录一旦不可用（临时目录清理、版本升级换 hash、安全软件搬移），按名加载失败 → 未处理异常 → 1026。
4. 官方同类记录：`dotnet/runtime#60144`、`RatScanner#247`，栈完全一致。

**修复**：新增 `src/AutoVolume.App/NativePin.cs`，启动时（任何 WPF 渲染之前）按全路径 `LoadLibrary` 该 DLL 并**永不释放**，退出期的按名加载就会命中已加载模块。路径取自 `AppContext.GetData("NATIVE_DLL_SEARCH_DIRECTORIES")`；非单文件构建自然退化为按名加载，失败也不影响运行。

**顺带修的 UX 问题**：原 `UnhandledException` 处理器无条件弹模态框，退出期崩溃会弹「AutoVolume 出错」并卡住收尾（2026-10-23 02:32 截图证据）。现在 `_exiting`（`ExitApp` 首行置位）或 `Environment.HasShutdownStarted` 为真时只写日志 `退出期异常，不弹窗（进程已在收尾）`。

**验证**：

| 用例 | 做法 | 结果 |
|---|---|---|
| 对照（关闭固定） | 运行中把解压目录改名 → `--exit-after` 正常退出 | **rc=127**，复现同一栈，随后日志 `退出期异常，不弹窗` |
| 修复（固定生效） | 同样改名 → 正常退出 | **rc=0**，`已固定 vcruntime140_cor3.dll` → `用户退出`，无崩溃行 |
| 正式配置 | 安装版 `--autostart --exit-after 6` | rc=0，`02:34:34 启动` → `02:34:40 用户退出`，事件日志零新增 |
| 不改目录正常退出 | 单文件连续退出 24 次（探针 20 + 产品 4） | 全部 rc=0 |

> 该异常不影响音量/播放恢复，但会留下 Windows 崩溃记录，旧版还会弹框挡住退出，因此按缺陷修。

## 7. 新需求接手流程

### 7.1 先判断类型

| 需求 | 改哪里 |
|---|---|
| 支持一个新播放器/视频源 | 先测 SMTC + 会话，再改配置默认值（多数不用改代码） |
| 改变触发/恢复时机 | `Core/Engine.cs`，Runtime 只执行 |
| 改变音量行为 | `Runtime/VolumeFader.cs` + `AutoVolumeRuntime.ApplyVolumeAsync` |
| 设置页/托盘交互 | `AutoVolume.App` |
| 新平台能力（如切设备） | `AutoVolume.Audio` + 新接口 |

### 7.2 加一个源应用

1. 跑 `spike probe` 看进程名、会话、峰值；`spike smtc list` 看是否有 SMTC。
2. 定关闭判据：有 SMTC → 默认；无 SMTC → 进程退出；常驻进程 → `closeSignal=window`。
3. 改 `Config.CreateDefault()` 的 `roles` 与 `video` members；同步改现有用户配置。
4. 实测「播放 → 暂停 → 关闭」，确认日志出现 `源有声` / `暂停确认` / `全部源关闭` / `恢复播放`。
5. 跑 `spike monitor --interval 100` 留一份 CSV 到 `logs/`。

### 7.3 加一个受控播放器

1. `spike smtc pause <exe>` / `play <exe>` 必须返回 True；否则查 AUMID。
2. UWP（如媒体播放器）：从 `Get-AppxPackage | Get-AppxPackageManifest` 取 `Executable` 与 `Identity.Name`；若 AUMID 与 exe 无包含关系，加到 `SmtcService.AumidAliases`。
3. 配置：`roles[exe]="controlled"`、`music.members` 加入、`control[exe]={method:"auto"}`。
4. 验证暂停确认耗时、恢复是否成功、会话静音是否覆盖尾音。

### 7.4 改行为

- 先写清“输入快照 → 期望动作”，改 `Engine.Tick`；
- 不允许在 Engine 里读系统状态或等待；
- 改完用 spike 构造/录制快照验证，再真机跑。

### 7.5 发布与推送

```bat

scripts\publish.cmd
copy artifacts\portable\AutoVolume.exe "%LOCALAPPDATA%\Programs\AutoVolume\"
```

- [ ] 配置未被误学习改写（music/video 值仍不同）

### 8.5 GitHub 推送（本机特有）

本机 `github.com` DNS 指向不可用 IP，API 正常、网页/ git 不通。推送前：

```bat
python C:\Users\zeroy\.local\ghproxy.py
set HTTPS_PROXY=http://127.0.0.1:8899
git push origin main
```

- 代理是 `CONNECT` 隧道，把 `github.com` 固定到可用 IP；**代理跑一段时间后会 502，重启即可**；
- 已登录 gh：`C:\Users\zeroy\.local\gh\bin\gh.exe`，token 在 `%APPDATA%\GitHub CLI\hosts.yml`（scope: repo）；
- Release 上传走 `api.github.com` / `uploads.github.com`，不需要代理；
- 远端地址用 `https://github.com:443/...` 绕开全局 `insteadOf` 的 ghproxy 改写。

**2026-10-23 实测补充（0.3.13 发布时踩到的两个坑）**：

1. **环境里已有一个系统代理**（`https_proxy` 指向 127.0.0.1:62961）。curl/git **优先读小写** `https_proxy`，只设 `HTTPS_PROXY` 会被它压掉，表现为 `CONNECT tunnel failed, response 502`——其实不是本地代理挂了。四个变量一起覆盖才生效。
2. **gh 的凭据助手只认 `host=github.com`**，远端写成 `github.com:443` 时它返回空 → `could not read Username`。用一次性 URL 归一即可：

```bat
set https_proxy=http://127.0.0.1:8899
set HTTPS_PROXY=http://127.0.0.1:8899
git -c "url.https://github.com/.insteadOf=https://github.com:443/" ^
    -c "credential.helper=!C:\Users\zeroy\.local\gh\bin\gh.exe auth git-credential" ^
    push origin main
```

（`insteadOf` 只重写一次，不会连锁改到 ghproxy.net；推送中出现 `Recv failure` 也先 `ls-remote` 核对，本次故障时远端其实已更新成功。）

## 11. 附：关键实测结论（别重复踩）

| 项 | 结论 |
|---|---|
| QQ 音乐 SMTC | 可用；暂停确认 54–120 ms |
| 网易云 SMTC | 可用；AUMID = `cloudmusic.exe` |
| Win11 媒体播放器 | exe `Microsoft.Media.Player.exe`；AUMID `Microsoft.ZuneMusic_8wekyb3d8bbwe!Microsoft.ZuneMusic`；必须别名 |
| Edge 关标签 | SMTC 265 ms 内消失；音频会话残留 Inactive |
| VLC | 无 SMTC；只能按进程退出判关闭 |
| 速览 | 有 SMTC 但关闭后残留；必须看窗口；峰值仅 0.005–0.01 |
| 设备切换 | 会话空窗 136 ms，峰值恢复 352 ms |
| 休眠 79.5 s | 会话/端点/音量/SMTC 完好 |
| 进程退出 | 音频会话残留 20 s+，必须 PID 验活 |
| 端点回读 | 密集写入后返回排队旧值，不可用于判定用户操作 |
| 尾音 | QQ 音乐淡出约 1.05 s，暂停确认后仍在响 |
| 自包含单文件 | SMTC 可读；压缩会使私有工作集 14→90 MB |
| 退出期 CRT | `vcruntime140_cor3.dll` 全程不加载、`ProcessExit` 才按名延迟加载；解压目录不在即 1026 崩溃。启动固定即可（NativePin） |
