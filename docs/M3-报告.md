## 2. 打包方案选择（关键：压缩会让内存翻 6 倍）

四种方式实测，代码完全相同：

| 打包方式 | 体积 | 私有工作集 | 安装后首次启动 | 热启动 |
|---|---|---|---|---|
| 单文件 + 压缩（初版） | 74.4 MB | **90.6 MB** | 2.32 s | 0.735 s |
| **单文件 + 不压缩（采用）** | **178.6 MB** | **14.0–15.1 MB** | 3.66 s | **0.53 s** |
| 自包含目录（非单文件） | ~190 MB | 13.1 MB | — | — |
| Debug 框架依赖（对照） | — | 13.0 MB | — | — |

**结论：`EnableCompressionInSingleFile=true` 会多占约 76 MB 私有工作集（90.6 vs 14.0），直接破坏 ≤80 MB 的内存指标。**
代价是体积从 74 MB 涨到 179 MB、首次启动从 2.3 s 涨到 3.7 s（冷缓存 + Defender 扫描）。

- 内存是硬指标，体积不是 → **关闭压缩**。
- 热启动 0.53 s 到运行时、0.60 s 就绪，满足 ≤1.5 s。
- 首次 3.7 s 只发生在安装/升级后第一次；同一文件第二次起 0.53 s。
- 如需更小体积，可选自包含目录（13 MB 内存，但要带 200+ 个文件），或日后加 PublishReadyToRun。

## 11. 0.3.2 修复：保存配置导致设置窗口卡死

### 现象

2026-10-20 03:01，日志停在：

```
03:00:57.047 QQMusic.exe 已暂停
03:01:12.458 检测到上次未正常退出：恢复 QQMusic.exe
```

再没有任何后续行；`uiadump "AutoVolume 设置"` 10 秒超时、零输出，进程 `Responding=True` 但 UIA 完全不响应。

### 原因（两个叠加）

1. `ReloadAsync`（保存配置触发）调用了 `Start()`，`Start()` 里又跑 `RecoverIfNeeded()`。
   此时磁盘上的 `journal.json` 是**当前会话 15 秒前自己写的**（正在挂起中），被当成"上次未正常退出"。
2. `RecoverIfNeeded` 用 `_smtc.TryPlayAsync(exe).GetAwaiter().GetResult()` 同步等待；
   而 `TryPlayAsync` 内部 `await s.TryPlayAsync()` 捕获了 UI 的 `SynchronizationContext` →  UI 线程等任务、任务等 UI 线程，死锁。

### 修复

| 点 | 改动 |
|---|---|
| 只跑一次 | `_recoveryAttempted` 标志；`Reload` 不再触发自愈 |
| 不阻塞 | `StartAsync()` 全异步，`Start()` 仅后台启动；删除 `GetAwaiter().GetResult()` |
| 有上限 | 单个播放器 `WaitAsync(3s)`，超时记日志后跳过 |
| 兜底 | `SmtcService` 的 `TryPauseAsync` / `TryPlayAsync` 加 `AsTask().ConfigureAwait(false)` |
| 入口 | WPF `OnStartup` 用后台 `StartRuntimeAsync()`，托盘先出现，自愈在后台跑 |

### 验证

| 用例 | 结果 |
|---|---|
| 启动时存在 journal | `检测到…` → `自愈：恢复 QQMusic.exe` → `运行时已启动`，耗时 **89 ms**，journal 被清除 |
| 运行中写 journal 后点「保存」 | 只有 `运行时已启动` / `配置已重载`，**没有**自愈日志，journal 原样保留 |
| 设置窗口响应 | `uiadump` 775 ms 返回 52 个元素（卡死时 10 s 超时 0 输出） |
| CLI 启动路径 | `--dev --seconds 4`，3 ms 进入运行时，状态 `Idle`、`smtc=ok` |

## 12. 0.3.3 响应优化：进入视频更快

### 改了什么

| 项 | 改动 |
|---|---|
| 两档确认 | 峰值 ≥ `fastPeakThreshold`(0.02) → 只等 `fastConfirmMs`(600ms)；弱信号（速览 0.005–0.01）仍等 `confirmMs`(1500ms) |
| 确认不反复 | 新增 `_confirmedSources`：确认后本轮发声内不再因瞬时峰值回落而取消 |
| 可关闭 | 设置页「时间参数」新增「明显有声时快速确认」，存 `fastConfirmEnabled`；关闭后一律等满 `confirmMs` |
| 峰值取最大 | `_maxPeak` 记录本轮最大峰值，避免抖动导致快/慢通道来回切 |

### 实测（VLC 播 30 s 正弦测试音，峰值 0.25；spike monitor 100 ms 采样）

| 环节 | 结果 |
|---|---|
| 首次峰值（CSV） | `03:16:00.626` |
| 快速确认日志 | `03:16:01.538` → 出声到确认 **912 ms**（含 0–500 ms 首次检测延迟） |
| 确认到暂停完成 | 55 ms |
| 暂停后静默 + 渐变 | 200 + 300 ms |
| 整链 | 约 **1.2–1.5 s**（原 1.5 s 确认 + 同流程约 2.1 s） |
| 关闭开关后 | 日志不再出现「快速确认」，回到 1.5 s 路径 |
| 保存 | `config.json` 写入 `fastConfirmMs=600 / fastPeakThreshold=0.02 / fastConfirmEnabled=true` |

> 剩余延迟主要是空闲轮询的首次检测（0–500 ms）。再往下压需要 WASAPI 会话事件唤醒，属于 P1。

### 0.3.4 → 0.3.5：悬停崩溃修复

0.3.4 发布后，鼠标悬停在 `?` 上会直接崩进程：

```
System.NotSupportedException: 默认情况下，ToolTip 属性不支持 StaysOpen 设置为 false 的 ToolTip 元素。
   at System.Windows.Controls.PopupControlService.ShowToolTip(...)
```

原因：`ToolTip` 仍挂在按钮的 `ToolTip` 属性上，`ToolTipService` 在悬停时会尝试自动弹出，而 WPF 明确禁止这种组合配 `StaysOpen=false`。

修复（0.3.5）：

| 点 | 改动 |
|---|---|
| 摘除服务 | 窗口构造时把 5 个 `ToolTip` 从 `Button.ToolTip` 取下存入 `_helpTips`，`ToolTipService` 不再接管，悬停不会自动弹 |
| 手动开关 | `OnHelpClick` 手动 `IsOpen=true`，`StaysOpen=true` 由代码控制 |
| 关闭时机 | 再点同一个 `?`、点窗口其他位置（`OnPreviewMouseDown`）、Esc、窗口失焦（`OnDeactivated`）都关闭 |
| 测试工具 | spike 的 `click` 实际是 `keys click x y`；`ClickAt` 补 DPI 感知（否则 125% 缩放下坐标被二次缩放）。新增 `uiarect`、`move`、`cursor`、`screencap` |

验证（Release 0.3.5）：

- 悬停 `?` 2 秒：进程存活，日志无新崩溃；
- 点击 `?` → 气泡出现；
- 再点同一个 `?` → 关闭；
- 点「时间参数」标题 → 关闭。

## 15. 0.3.7 尾音修复：暂停后音乐先变大再消失

### 现象

网页视频开始时，QQ 音乐已经"暂停"，但还能听见约 1 秒的尾音，而且**先变大再消失**。

### 实测原因

用 20 ms 采样记录暂停前后的 QQ 音乐峰值：

| 时间 | 峰值 | 状态 |
|---|---|---|
| 04:26:23.670（SMTC 报 Paused） | 0.960 | Active |
| 04:26:23.977 | 0.746 | Active |
| 04:26:24.349 | 0.276 | Active |
| 04:26:24.719 | 0.000 | Active |

**暂停确认到真正静音约 1.05 秒**——QQ 音乐暂停时会自己做淡出，SMTC 先报 Paused，音频后停。

旧时序：暂停确认 → 等 200 ms → 300 ms 渐变到视频音量。渐变正好落在尾音区间（峰值 0.7→0.34），把淡出**放大**了，所以听起来"先变大再没了"。

单纯加长等待会牺牲响应速度，且尾音长度不稳定。

### 修复

新增 `src/AutoVolume.Audio/SessionVolumeController.cs`：用 `ISimpleAudioVolume` 把被暂停应用的音频会话静音。

| 时机 | 动作 |
|---|---|
| 暂停确认后 | 立即静音该应用会话（尾音哑掉），等 80 ms（原 200 ms）就切主音量 |
| 恢复播放前 | 先解除静音再 `TryPlay` |
| 1.5 s 后 | 自动解除（带代数校验，防止新一局被误解除；也避免崩溃后应用一直哑着） |
| 引擎让权 / 用户手动播放 | 每 tick `UnmuteExcept(PausedByUs)` 自动解除 |
| 退出 / 崩溃自愈 | `Dispose`、`RestoreAllAsync`、`RecoverIfNeededAsync` 都会解除静音 |
| 用户原本手动静音的应用 | 只恢复自己改过的会话，不动用户的静音设置 |

### 验证（Release 0.3.7）

| 用例 | 结果 |
|---|---|
| 视频开始 → 暂停音乐 | 会话静音 `muted=True`，覆盖整个淡出区间 |
| 1.5 s 后 | 自动回到 `muted=False` |
| 视频关闭 → 恢复音乐 | `muted=False`，SMTC `Playing`，峰值 0.46 |
| 暂停→切音量耗时 | 80 ms settle（原 200 ms），比之前更快 |

## 16. 0.3.8 关闭视频后音量不切换

### 现象

用户反馈：关闭视频后系统音量不再回落，几次之后完全听不出切换。

### 日志与数据

配置 `fadeMs=100`。50 ms 采样一次主音量，一次视频开始的记录：

| 时间 | 主音量 |
|---|---|
| 19.585 | 0.083（渐变开始） |
| 19.645 | 0.121 |
| 19.707 | **0.120（最终落点，目标 0.140）** |

随后日志出现 `学习音量 video = 0.120`，把方案里的 0.14 覆盖成 0.12。

同一现象可脱离应用复现：用 spike 以 100 ms 渐变 0.08 → 0.14，命令自身回读 0.14，0.4 s 后实测 **0.12**；300 ms 渐变则稳定落 0.14。

### 根因

- 100 ms / 8 步 ≈ **12 ms 一次** `SetMasterVolumeLevelScalar`，音频端点会把密集写入合并，最后一步在 30–50 ms 后回弹到中间值。
- `VolumeFader` 写完后立即回读，拿到的是缓存值 0.14，日志按目标值记「成功」。
- 约 0.5 s 后 `CheckUserVolumeChange` 读到真实值 0.12，与 `LastWritten`（0.14）不符 → 判定为用户手动调整 → **学习并保存**。
- 反复几次后 music 与 video 都被学成同一个值（日志里出现过 0.2/0.2），切换自然没有任何声音变化。

### 修复

| 点 | 改动 |
|---|---|
| 写入间隔 | `stepDelay` 下限从 1 ms 提到 **25 ms** |
| 结束校验 | 写完等 **120 ms** 回读，偏差 >0.005 就补写，最多 3 次 |
| 记录值 | `LastWritten` 一律取实际回读值，避免污染学习判定 |
| 失败上报 | 仍不到位时返回 false，`LastAbort = final=… target=…` |

### 验证

| 项 | 结果 |
|---|---|
| Debug（fadeMs=100） | 视频开始 → 0.1400；关闭 → 0.0800；无「学习」误报 |
| Release 0.3.8 | 同样 0.1400 / 0.0800 |
| 配置修复 | 已被学坏的 music/video 重置为 0.08 / 0.14 |
