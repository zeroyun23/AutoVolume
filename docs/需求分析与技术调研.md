## 2. 音量归属（v0.8 新增，重要）

之前写的是"最近开始发声的方案优先"，这会出一个问题：用户在看视频时手动恢复音乐，音量会突然跳回音乐方案，视频被压低。**改成只看监测源。**

### 2.1 归属规则

```
有监测源在响？
  ├─ 是 → 取「最近开始发声的源」所属方案的音量
  └─ 否 → 有受控播放器在播？
           ├─ 是 → 取该播放器所属方案的音量
           └─ 否 → 取默认方案（通常是音乐）的音量
```

推论：

- 音乐被暂停时不算发声，不会抢归属。
- 用户手动恢复音乐、视频还在响 → 音量仍归视频方案，音乐在 15 的音量下响。这是用户手动干预的代价，行为可预测。
- 两个源同时响 → 最近开始的那个说了算；它停了，退回到另一个仍在响的源。
- 源和播放器分属不同方案时，永远优先源。

### 2.2 默认方案

配置里加一个 `defaultScheme`（默认 "music"）。**没有任何东西在响时，音量归它。**

如果没有设默认方案，就完全不动音量——不要猜。

### 2.3 渐变与用户抢夺

- 切方案：`SetMasterVolumeLevelScalar` 分 8 步、300 ms 缓动。
- 渐变过程中用户拖动音量条 → **立即取消渐变**，以用户值为准，并更新当前方案的音量值。
- 判断"用户操作"：目标值与我们的写入值相差 >2%，且在写入后 500 ms 之外。

## 3. 检测

- `IAudioSessionManager2` 枚举会话，只保留角色为监测源的进程。
- 50 ms 读 `IAudioMeterInformation::GetPeakValue()`。
- 有声：峰值 > 0.01（-40 dBFS）持续 ≥1.5 s。
- 不用 `Active/Inactive` 判定"有声"（滞后 + 静音流），但**用它判定"是否在播"**（见 §5.2）。
- 静音视频不产生峰值，不触发。
- 独占模式播放器无会话，检测不到。

## 4. 互斥与恢复

### 4.1 严格模式：什么算"关闭"

| 信号 | 含义 | 算关闭 |
|---|---|---|
| 进程退出（含崩溃） | 播放器/浏览器没了 | ✅ |
| 音频会话消失，30 s 内未重建 | 关标签、文件停止 | ✅ |
| SMTC `Closed` | 媒体关闭 | ✅ |
| SMTC `Stopped` | 播完，窗口还在 | ❌ |
| `Paused` / 峰值 0 | 暂停 | ❌ |
| 会话在、进程在、没声 | 播完没关 | ❌ |

### 4.2 三种"假关闭"必须防（v0.8 新增）

以下情况会让所有音频会话瞬间消失，如果直接判定"关闭"，音乐会在错误的时机恢复：

| 场景 | 现象 | 处置 |
|---|---|---|
| **切换输出设备**（插耳机、蓝牙连接） | 旧 endpoint 的会话全部失效 | 监听 endpoint 变化，进入 **5 s 抑制窗口**；窗口内不判关闭；结束后重新枚举，源仍存在则忽略本次 |
| **系统休眠/唤醒** | 音频会话被销毁重建 | 同上，唤醒后 5 s 抑制 |
| **音频服务重启**（audiosrv 崩溃） | 全部会话消失 | 检测服务状态或枚举失败，进入 10 s 抑制，恢复后重绑 |

**原则：宁可晚 5 秒恢复，也不要误恢复。**

### 4.3 关闭后也要等 T

严格模式不是"一关就恢复"。关闭判定成立后，仍然等 T 秒（默认 3 s）：

- 防止"关掉第一集、第二集还在加载"时音乐插进来；
- 期间出现新的源 → 取消恢复，继续互斥；
- T 设 0 就是立即恢复，界面提示乒乓风险。

### 4.4 宽松模式

所有源连续 T 秒没有声音（暂停/播完/关闭都算）→ 恢复。不判关闭，实现更简单。

### 4.5 多源

- 互斥：任一源有声就暂停。
- 严格恢复：所有源都关闭才恢复。
- 宽松恢复：所有源静音 T 秒才恢复。

### 4.6 恢复顺序（v0.8 新增）

```
1. 等 T 秒，无新源
2. 主音量渐变到播放器所属方案（300 ms）
3. 渐变结束后，再恢复播放
```

先还原音量再恢复，避免以视频的 15 起播音乐导致"一开口就炸"。总延迟约 300 ms，可接受。

进入视频时顺序相反：**先暂停音乐，再升音量**。否则音乐会在暂停完成前被放大 300 ms。

## 5. 控制

```
SMTC 定向暂停 → 全局热键 → 失败（不改音量、不改状态、托盘提示）
```

### 5.1 受控播放器的准入门槛

添加时必须点"测试暂停"：真停住才允许保存。测不通直接标红，不许加入。没有静音兜底，加进来也是摆设。

### 5.2 热键播放器的状态判定（v0.8 新增）

热键是 toggle，必须先知道当前状态。**用会话状态，不要用峰值**：

| 判断目的 | 依据 |
|---|---|
| 是否在播 | `IAudioSessionControl::GetState() == Active` |
| 是否真的出声 | 峰值 > 0.01 |
| 暂停条件 | 状态 Active，且最近 2 s 内有峰值 |
| 恢复条件 | 只恢复"我们暂停过的"（`pausedByUs` 表） |

原因：安静段落峰值 = 0，但会话仍是 Active，用峰值判断会漏暂停。

发送后 300 ms 复查：状态变 Inactive 或峰值归零 → 成功；否则记为失败并停止重试（防止反复 toggle）。

### 5.3 提权与多实例

- 目标以管理员运行 → `SendInput` 被 UIPI 拦，标记"不可控"。
- 同一播放器开多个实例 → 热键可能被多个实例响应，导致双重 toggle。检测到多实例直接禁用该播放器的热键路径，提示只保留一个实例。

## 10. 资源占用与架构选型

### 10.1 结论

**推荐：C# .NET 8 + WPF 托盘应用。**

预期常驻内存 50–75 MB，空闲 CPU <0.3%，自包含安装包 60–90 MB。对你 32 GB 内存的机器来说这是背景噪声——Edge 一个浏览器就 300–800 MB，QQ 音乐自己也要 200 MB 上下。

### 10.2 开销从哪来

| 项目 | 预期 | 说明 |
|---|---|---|
| .NET 运行时 + GC | 25–35 MB | 无法避免，除非换原生 |
| WPF 框架 | 15–25 MB | 设置窗口按需创建、关闭即释放可压到下限 |
| 应用对象 + 会话缓存 | 3–8 MB | 只有 2–4 个会话对象 |
| 托盘图标 + 定时器 | <1 MB | — |
| **合计私有工作集** | **50–75 MB** | 任务管理器"内存"列通常显示 60 MB 左右 |

CPU：

| 操作 | 频率 | 单次成本 | 占比 |
|---|---|---|---|
| 读会话峰值 | 20 次/秒 × 3 路 | 1–3 µs | <0.02% 单核 |
| 会话枚举 | 仅设备变化时 | 毫秒级 | 可忽略 |
| 音量渐变 | 仅切换时 8 次写入 | 微秒级 | 可忽略 |
| 状态机 | 20 次/秒 | 纳秒级 | 可忽略 |

**真正需要注意的是"唤醒次数"，不是 CPU 占比。** 50 ms 轮询 = 每秒 20 次唤醒，会让笔记本难以进入深度 C-state，轻微费电。

**对策：自适应轮询。**

- 没有源会话处于 Active → 500 ms 轮询一次，或干脆挂起，只等 `IAudioSessionEvents` 事件；
- 有源会话 Active → 升到 50 ms；
- 源会话消失 → 降回低频。

这样待机时几乎零唤醒，播放时才高频。

磁盘：稳态几乎不写盘。配置只在变更时写，journal 只在状态迁移时写，日志滚动上限 5 MB。

### 10.3 技术方案对比

| 方案 | 私有工作集 | 安装体积 | 空闲 CPU | 开发成本 | 适配度 |
|---|---|---|---|---|---|
| **C# .NET 8 + WPF**（推荐） | 50–75 MB | 60–90 MB 自包含 | <0.3% | 中 | ★★★★★ |
| C# .NET 8 + WinForms | 35–50 MB | 50–70 MB | <0.3% | 低 | ★★★★（UI 弱） |
| C++ / Win32 + C++/WinRT | 8–15 MB | 2–5 MB | <0.1% | 高（3–5 倍） | ★★★ |
| Rust + windows crate | 10–20 MB | 3–6 MB | <0.1% | 高 | ★★★ |
| Go + systray | 20–30 MB | 10–15 MB | <0.2% | 中高（SMTC 绑定差） | ★★ |
| Python + pycaw + PyQt | 80–150 MB | 40–80 MB | 1–3% | 低 | ★★ |
| Electron / Tauri | 80–150 MB / 40–60 MB | 100 MB+ / 10 MB | 0.5–2% | 中 | ★（为 UI 引入 WebView，重） |
| WinUI 3 | 80–120 MB | +50 MB Windows App SDK | <0.5% | 中 | ★★★（不值） |

**为什么不是 C++：** 体积确实小一个数量级，但你要做设置页、分组列表、音量条、日志窗口，Win32 手写 UI 的成本是 WPF 的 3–5 倍。这个工具的价值在逻辑稳定，不在省 50 MB。

**为什么不是 Python：** 原型最快，但常驻 100 MB+、打包后启动慢、托盘体验差。你之前定位是"长期开机自启"，不适合。

**为什么不是 WinUI 3：** 多背 50 MB 的 Windows App SDK，内存反而更高，外观优势对托盘工具没意义。

### 10.4 推荐架构

```
┌──────────────────────────────────────────────┐
│ Host（WPF App / 托盘 / 单实例 / 自启）        │
├──────────────────────────────────────────────┤
│ Core（状态机，纯逻辑，可单测）                 │
│   事件 → 状态迁移 → 指令（暂停/恢复/改音量）   │
├───────────────┬──────────────┬───────────────┤
│ Detection     │ Control      │ Volume        │
│ WASAPI 会话    │ SMTC 驱动    │ 端点音量       │
│ 峰值 / 事件    │ 热键驱动      │ 渐变 / 锚点    │
├───────────────┴──────────────┴───────────────┤
│ Config（JSON，exe 名匹配，原子写）             │
│ Journal（崩溃自愈）                            │
└──────────────────────────────────────────────┘
```

关键实现点：

1. **线程模型**：UI 用 STA；WASAPI 单独一个 MTA 线程，所有 COM 对象只在该线程创建与释放，不要跨线程传递接口指针。
2. **COM 生命周期**：会话对象缓存，但要处理 `Expired`；枚举器在设备变化时整体重建。
3. **WinRT 调用**：目标框架设为 `net8.0-windows10.0.19041.0`，直接引用 `Windows.Media.Control`，不需要额外 NuGet。
4. **音频接口**：用 NAudio 起步（开发快），性能敏感处再换 CsWin32 生成的裸 interop。
5. **单实例**：命名 Mutex；第二实例唤起设置窗口后退出。
6. **配置原子写**：写临时文件 → `File.Replace`，避免断电损坏。
7. **自启**：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，延迟 10 s 启动，避开开机高峰。
8. **发布**：自包含单文件 + 压缩；不开 trimming（WPF 不支持，会炸）。

### 10.5 性能验收线

| 指标 | 目标 |
|---|---|
| 空闲 CPU | ≤0.3% |
| 播放中 CPU | ≤1% |
| 私有工作集 | ≤80 MB |
| 启动到可工作 | ≤1.5 s |
| 稳态磁盘写入 | 0（日志除外） |
| 待机唤醒 | ≤2 次/秒（自适应后） |

## 11. 开发与发布策略

### 11.1 结论：安装版不影响调试，但开发期别用安装版

调试跑的是源码输出目录，跟你发不发安装包没有任何关系。断点、单步、热重载都在 `bin\Debug\` 里进行。安装版带来的麻烦只有三处：

1. 覆盖安装时，运行中的托盘程序会锁住 exe，必须先退出；
2. 自启注册表指向安装路径，开发时重建不会生效；
3. 配置写进 `AppData`，调试期间反复污染，清理麻烦。

**做法：开发期用 Debug 目录，自用测试用便携版，UI 稳定后再打安装包。**

### 11.2 三种构建形态

| 形态 | 用途 | 产物 | 特点 |
|---|---|---|---|
| Debug | 日常开发 | `bin\Debug\net8.0-windows\` | F5 直跑，断点 + XAML 热重载 |
| 便携 Release | 自用 / 内测 | 单文件 exe，配置同目录 | 解压即用，替换方便，不写注册表 |
| 安装包 | 分发给别人 | exe + Inno Setup/NSIS | 开始菜单、自启、卸载 |

### 11.3 开发期必须做的五个隔离

不隔离会浪费大量时间在"为什么改了没生效"上。

| 项 | 问题 | 做法 |
|---|---|---|
| 配置目录 | 开发数据写脏真实配置 | `--dev` 时用 `%LOCALAPPDATA%\AutoVolume-dev` |
| 单实例 Mutex | 调试时第二个实例起不来 | `--dev` 时 Mutex 名加后缀 |
| 开机自启 | 每次重建都改 Run 键指向 bin 目录 | `#if DEBUG` 禁止写注册表 |
| 崩溃自愈 | 断点暂停被当成崩溃，自动恢复音量 | 加 `--no-recovery` |
| 日志 | 刷屏、占盘 | 开发级 Debug，滚动上限 5 MB |

### 11.4 调试体验

- **VS2022 + XAML Hot Reload**：改样式、改布局不用重启；改逻辑仍需重启。
- **`--diag` 控制台模式**：托盘程序默认没窗口，加一个诊断模式直接打印会话表、峰值、状态机迁移，调检测逻辑时不用开 UI。
- **`--fake` 模拟源**：注入假峰值序列，测边界（缓冲、切集、假关闭）不用真放视频。
- **状态机单测**：纯逻辑 + 假时钟，覆盖全部迁移，不依赖真实音频设备。

### 11.5 发布与更新

- 先出**便携版 zip**，自用完全够，替换就是覆盖文件。
- 安装包等 UI 定稿再做，Inno Setup 半天能搞定。
- 个人工具不需要自动更新。后期要加，做"检查版本 → 下载 → 提示替换"即可，别上 Squirrel 那套。
- 托盘程序替换 exe 前必须先退出，否则文件占用——这一点在开发期最烦，所以更要便携。

## 12. Rust 方案评估

### 12.1 结论

**能做，但省下的 50 MB 换不回开发效率。** 除非你有明确的体积/内存硬指标（比如必须做成 5 MB 绿色单文件），否则不建议。

### 12.2 四个真正的难点

| 领域 | Rust 现状 | 难度 |
|---|---|---|
| **GSMTC / WinRT** | `windows` crate 有生成绑定，但 `IAsyncOperation` 要手动 `get()` 或接 `windows-future`，apartment 规则得自己管 | 中高 |
| **WASAPI** | `windows` crate 是裸 COM，vtable 调用冗长；`wasapi` crate 做了播放/采集封装，但**不覆盖会话枚举**，仍要自己写 | 中高 |
| **COM 回调**（会话事件） | `#[implement]` 能实现 `IAudioSessionEvents`，但样板多、引用计数和生命周期容易踩坑 | 高 |
| **UI** | 没有 WPF 级别的方案，详见下表 | 高 |
| 中文渲染 | egui 默认字体不含 CJK，要么打包字体（+5–10 MB），要么手动加载系统字体 | 中 |
| 托盘 / 通知 / 自启 | `tray-icon`、`winrt-notification`、`auto-launch` 都有，但生态碎片化，踩坑要自己填 | 中 |

### 12.3 UI 选项对比

| 方案 | 内存 | 体积 | 观感 | 问题 |
|---|---|---|---|---|
| egui / eframe | 30–60 MB | 5–10 MB | 非原生 | 即时模式，写列表表单快，细节粗糙，无障碍差 |
| slint | 40–70 MB | 8–15 MB | 较好 | GPL / 商业双许可，商用要注意 |
| Tauri（wry） | 50–90 MB | 8–15 MB + WebView2 | 好 | 本质是 WebView，内存一点不省，还多一层 IPC |
| 原生 Win32 | 10–20 MB | 3–6 MB | 原生 | 控件全手写，工期爆炸 |

**注意：Rust 省内存的前提是"UI 也用轻量方案"。** 一旦上 Tauri，内存和 C# 打平，优势只剩体积。

### 12.4 工期与风险

- 同样功能，Rust 约为 C# 的 **2–3 倍**，时间主要耗在 UI 和 COM 回调。
- GSMTC 的异步模型在 Rust 里要自己处理阻塞与 apartment，卡几天很正常。
- 调试：VS Code + CodeLLDB 能用，但 COM/WinRT 的断点体验明显不如 C#。
- **没有可抄的先例**：同类开源项目 Tuner、Interlude 都是 C#，Python 的 Music-Pause 也没碰 SMTC 写指令。

### 12.5 什么情况下选 Rust

- 目标是 5 MB 级绿色单文件，UI 只要托盘菜单 + 一个简单设置窗；
- 能接受 egui 的观感；
- 不赶时间，愿意为 COM 调试付费。

否则 C#。

### 12.6 不推荐的折中

"C# 先做 MVP，稳定后用 Rust 重写核心"——重写成本高于收益，除非准备长期分发。音频状态机与 UI 耦合不深，但 COM/WinRT 层重写等于重做一半。
