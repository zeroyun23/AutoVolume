## 0. 30 秒读懂

**做一个 Windows 托盘小工具：网页或本地播放器出声时，自动暂停 QQ 音乐/网易云音乐；视频关闭后自动恢复音乐，并把系统音量切回该场景的音量。**

| 项 | 结论 |
|---|---|
| 技术栈 | **C# .NET 8 + WPF**（已定，不再讨论 Rust/C++） |
| 检测 | 白名单应用的 WASAPI 音频会话峰值 + 自适应轮询 |
| 控制 | GSMTC（SMTC）定向暂停 → 应用全局热键 → 失败提示（**没有静音兜底**） |
| 音量 | 系统主音量，按「音量方案」切换，300 ms 渐变 |
| 发布 | **先便携版**（单文件 exe），安装包后置 |
| 当前阶段 | M0–M2 已完成；下一步 Release 打包 + 自启验证 + 日志轮转（见现状文档 §10） |

## 1. 背景与调研结论（为什么这样做）

### 1.1 根因

Windows 没有 Android 式的音频焦点机制。同一输出设备上的所有音频会话默认硬混音，没有优先级、没有抢占。系统唯一的"自动压低"是"通信活动时降低其他声音 80%"，只对通话/会议流生效，网页视频不算。

### 1.2 为什么不能用媒体键

`VK_MEDIA_PLAY_PAUSE` 发给"当前媒体会话"，不是指定应用。视频一开始，浏览器就是当前会话，此时发媒体键暂停的是视频。

| 场景 | 播放/暂停键去向 |
|---|---|
| 只有音乐在播 | 音乐软件 |
| 浏览器最近播过视频 | 浏览器 |
| 视频暂停但标签没关 | 仍常常是浏览器 |
| 多个应用在播 | 最近活动的会话 |

只能用两种定向手段：**SMTC 定向指令**（可指定 session、可回读状态）或**应用自己的全局热键**（`RegisterHotKey` 系统级、定向到注册者）。

### 1.3 同类项目（调研结论）

| 项目 | 语言/Star | 能力 | 差距 |
|---|---|---|---|
| woodtong/Tuner | C# / 1★ | 分组闪避、SMTC 事件驱动、锚点保护 | 只压低不暂停，无音量方案 |
| ZephyrWn/Interlude | C# / MIT / 0★ | GSMTC 暂停恢复、三种检测模式 | 单播放器，无音量方案 |
| SNALYF/Music-Pause | Python / 0★ | 浏览器视频→静音音乐客户端 | 只静音，不暂停 |
| Klocman/Automatic-Volume-Mixer | C# / 80★ | 规则化音量自动化 | 规则重，无场景记忆 |
| EarTrumpet / SoundSwitch | 11.5k★ / 3.4k★ | 每应用音量、设备切换 | 无自动化 |

**结论：暂停 + 音量方案 + 严格恢复，这个组合没有完整实现，值得自研。**

## 2. 需求（用户原话归纳）

### 2.1 场景

一边用 QQ 音乐听歌，一边打开网页视频。现在音乐和视频混在一起，必须手动暂停音乐、调大音量、看完再调回去。一次视频 3–4 次手动操作。

### 2.2 必须做到

1. 监测指定应用（浏览器、PotPlayer、VLC）是否在出声。
2. 出声时暂停受控播放器（QQ 音乐、网易云音乐）。
3. 关闭后恢复播放，并把系统音量切回音乐场景的音量。
4. 音量按"方案"区分：同一方案的应用共用一个音量值。
5. 首次进入某方案不动音量，用户调了才记住；之后沿用。
6. 恢复延迟可设（0–30 s），关闭后默认等 3 s。
7. 严格模式：页面/播放器没关，就不恢复音乐。
8. 托盘常驻、开机自启、崩溃自愈。

### 2.3 明确不做（已被用户否决，不要偷偷加回来）

| 不做 | 原因 |
|---|---|
| 媒体键 | 会打错目标 |
| 静音兜底（`SetMute`） | 播放进度继续走，体验差，用户明确取消 |
| 分组优先级 / 分组互斥 | 复杂度爆炸，三组以上会死循环 |
| 全量监听所有音频会话 | 微信/通知误触发，改白名单 |
| 分组控制语义 | 分组只做音量 |
| 自动更新 | 首版不做 |
| 注入 / Hook / 读内存 | 合规风险 |
| 修改应用内音量滑块 | 会与应用 UI 打架 |
| 10 分钟"忘了关"提醒 | 用户明确不需要 |

### 2.4 非功能要求

| 指标 | 目标 |
|---|---|
| 常驻私有内存 | 50–75 MB（可接受到 80 MB） |
| 空闲 CPU | ≤0.3% |
| 播放中 CPU | ≤1% |
| 启动到可工作 | ≤1.5 s |
| 稳态磁盘写入 | 0（日志除外） |
| 待机唤醒 | ≤2 次/秒（自适应轮询后） |

| 编号 | 决策 |

| D3 | 音量值按输出设备（endpoint）分别存 |

| D12 | 禁止同一应用兼任监测源与受控播放器 |
| D13 | 浏览器崩溃算关闭，恢复音乐 |
| D14 | 同一标签内换视频（会话不消失）不恢复 |
| D15 | 音量方案切换使用渐变（默认 300 ms） |

| D17 | 音量归属只看监测源；无源时归在播播放器；都无则归默认方案 |
| D18 | 默认方案 = 音乐方案 |
| D19 | 严格模式关闭后等 3 s 再恢复 |
| D20 | 假关闭防护：切设备 5 s、休眠 5 s、音频服务重启 10 s 抑制 |
| D21 | 恢复顺序：先渐降到目标音量，再恢复播放；进入视频先暂停再升音量 |
| D22 | 热键播放器用会话 `Active` 判在播，不用峰值 |
| D23 | 采用自适应轮询：无源 Active 时降频/事件驱动，有源 Active 时 50 ms |
| D24 | 接受约 60 MB 常驻内存，走 C# 路线 |

## 4. 产品模型（四个概念）

| 概念 | 一句话 |
|---|---|
| **角色** | 监测源 / 受控播放器，二选一，禁止兼任 |
| **音量方案** | 一组应用共用一个系统音量，只管音量 |
| **互斥开关** | 开：源一响就暂停播放器；关：只切音量 |
| **恢复策略** | 严格：关闭才恢复；宽松：没声音就恢复 |

### 4.1 角色

| 角色 | 含义 | 例子 |
|---|---|---|
| 监测源 | 它的声音触发暂停 | Edge、Chrome、PotPlayer、VLC |
| 受控播放器 | 被暂停/恢复的对象 | QQ 音乐、网易云音乐 |
| 未配置 | 完全不参与 | 微信、QQ、系统声音 |

同一 exe 只能有一个角色；既当源又当播放器 → 禁止保存并提示。

### 4.2 音量方案

- 一个方案 = 一组应用 + 一个系统主音量值。
- 同方案应用共用这个音量；不同方案可以有不同音量。
- 方案可增删，成员可改。
- 方案之间没有任何压制关系。

示例：

| 方案 | 成员 | 音量 |
|---|---|---|
| 音乐（默认） | QQMusic.exe、cloudmusic.exe | 0.10 |
| 视频 | msedge.exe、PotPlayerMini64.exe、vlc.exe | 0.15 |

### 4.3 互斥开关

| 状态 | 行为 |
|---|---|
| 开（默认） | 任一监测源有声 → 暂停所有受控播放器；按恢复策略恢复 |
| 关 | 只切换音量，不暂停任何人 |

### 4.4 恢复策略

| 策略 | 触发恢复的条件 |
|---|---|
| 严格（默认） | 所有监测源**关闭**（**SMTC 会话消失** / 进程退出；浏览器不靠音频会话消失） |
| 宽松 | 所有监测源**没有声音**持续 T 秒（暂停、播完、关闭都算） |

## 5. 行为规格

### 5.1 判定算法

```
每 50ms（自适应频率）：
  for 每个监测源进程：
      peak = max(peak(s) for s in sessions(进程))
      sounding = peak > 0.01

  candidates = [源 for 源 in 源列表 if sounding 连续 ≥ 1.5s]
  anySounding = candidates 非空

  if 互斥开启:
      if anySounding and 有受控播放器在播 and 未进入 SUSPENDED:
          暂停播放器 → 记入 pausedByUs
      if 恢复条件成立 and pausedByUs 非空:
          等 T 秒 → 渐降到目标音量 → 恢复播放
```

- 恢复条件：严格模式 = 所有源都关闭；宽松模式 = 所有源静音 ≥ T。
- 监测源关闭后，T 秒内出现新源 → 取消恢复（防切集乒乓）。
- 用户手动播放音乐 → `SUSPENDED_BY_USER`，本周期不再暂停，直到所有源关闭。

### 5.2 音量归属

```
有监测源在响？
  ├─ 是 → 取「最近开始发声的源」所属方案的音量
  └─ 否 → 有受控播放器在播？
           ├─ 是 → 取该播放器所属方案的音量
           └─ 否 → 取默认方案（音乐）的音量
```

推论：

- 音乐被暂停时不算发声，不抢归属。
- 用户手动恢复音乐、视频还在响 → 音量仍归视频方案。
- 两个源同时响 → 最近开始者优先；它停了退回另一个。

**2026-10-19 修正（实测抖动）：** 如果严格按"此刻峰值 > 0.01"归属，峰值稀疏的源（实测 PowerToys 速览预览视频）
会让音量在 video/music 之间反复跳，还会把用户的音量调整学进错误的方案。
现在改为：**挂起期间按"本轮响过且仍未关闭的源"归属**，取最近发声的那个；源关闭后才降回音乐方案。
副作用：视频暂停（窗口仍在）时音量保持视频方案，关闭后恢复——更符合"场景"直觉。

### 5.3 恢复顺序（必须按此顺序）

**退出视频：**

1. 等 T 秒，期间无新源；
2. 主音量渐变到播放器所属方案（300 ms，8 步缓动）；
3. 渐变**结束后**再恢复播放。

**进入视频：**

1. 先暂停音乐；
2. 再升音量到视频方案。

顺序反了会爆音或让音乐被放大 300 ms。

### 5.4 音量渐变与用户抢夺

- 渐变 8 步 / 300 ms。
- 渐变中用户拖动音量 → **立即取消渐变**，以用户值为准，并更新当前方案的值。
- 区分"用户操作"：目标值与我们的写入值相差 >2%，且在写入后 500 ms 之外。

### 5.5 严格模式：什么算关闭

**2026-10-19 实测（Edge 播 B 站视频，250 ms 采样）：**

| 状态 | 音频会话 | 峰值 | SMTC 会话 |
|---|---|---|---|
| 播放中 | `Active` | 0.13–0.33 | 存在，`Playing` |
| 暂停 | **`Active`** | **0.000** | 存在，**`Paused`** |
| 关闭标签 | **`Inactive`**（不消失） | 0.000 | **直接消失**，没有 `Closed` 过渡 |

**判定表：**

| 信号 | 判为 |
|---|---|
| 进程退出（含崩溃） | 关闭 |
| **SMTC 会话消失** | **关闭（Edge / Chrome 的主判据）** |
| SMTC `Stopped / Closed` | 关闭 / 播完（按策略） |
| SMTC 存在且 `Paused`，音频会话 `Active` | 暂停 |
| 音频会话 `Inactive`，进程仍在 | 关闭（浏览器） |
| 音频会话 `Active`、峰值 0 | 暂停（长暂停可能被浏览器释放流，需 SMTC 兜底） |

**三条必须记住的实测结论：**

1. **不要等音频会话消失。** Edge 关标签后仍保留一个 `Inactive` 空会话，至少 75 秒不消失，可能直到浏览器退出。按"会话消失"判关闭会永远等不到。
2. **不要指望 `Closed` 状态。** 实测是会话直接消失，没有经过 `Closed`。
3. 关闭检测延迟约 **265 ms**（采样精度内）。

> 对没有 SMTC 的源（如未装插件的 VLC），只能看音频会话状态：`Active + 峰值 0` = 暂停，`Inactive` = 关闭。这个规律来自 Chromium，能否套用到 VLC 必须单独实测。

**2026-10-19 补充实测（VLC 3.x，详见 `docs/spike-report.md`）：**

| 状态 | 音频会话 | 峰值 | SMTC |
|---|---|---|---|
| 播放中 | `Active` | 0.2500 | **无会话** |
| 暂停 | `Inactive` | 0.0000 | 无会话 |
| 停止播放（进程在） | `Inactive` | 0.0000 | 无会话 |
| 结束进程 | 残留 ~200ms 后消失 | — | 无会话 |

结论修正：**VLC 没有 SMTC，且 `Inactive` 只代表暂停/停止，不代表关闭。**
对无 SMTC 的源，严格模式的关闭判据只能是**进程退出**（`inactiveMeansClosedForNonSmtc = false`）。

**另一个坑（同日实测）：进程退出后音频会话可以残留 20 秒以上**（`Inactive`，进程名已解析为 unknown）。
所以「有会话」不能推导「进程活着」，必须按 PID 单独验活并比对进程名（防 PID 复用）。

**PowerToys 速览（Peek 0.99.1）实测：** 预览时有 SMTC 会话（AUMID `PowerToys.Peek.UI.exe`，`Playing`/`Paused`），
但 **Esc 关闭后会话不会消失，一直以 `Paused` 残留**；进程也常驻。音频会话在暂停与关闭时都是 `Inactive`。
因此 Peek 的关闭判据只能用**预览窗口是否存在**（配置 `closeSignal`，见 §7.3），不能套用 Edge 的 SMTC 消失判据。

### 5.6 假关闭防护

以下情况会让所有会话瞬间消失，必须抑制判定：

| 场景 | 抑制窗口 |
|---|---|
| 切换输出设备（插耳机/蓝牙） | 5 s，结束后重新枚举 |
| 系统休眠/唤醒 | 5 s |
| 音频服务重启 | 10 s |

原则：**宁可晚 5 秒恢复，不要误恢复。**

## 6. 技术架构

### 6.1 选型

**C# .NET 8 + WPF**。理由：

- GSMTC 是 Windows 运行时一等公民，`net8.0-windows10.0.19041.0` 可直接引用 `Windows.Media.Control`；
- WASAPI 有成熟封装（NAudio）+ 可手写 interop；
- WPF 做设置页、列表、音量条的成本远低于 Win32；
- 同类项目（Tuner、Interlude）都是 C#，可对照。

不用 Rust/C++/Python/WinUI3 的理由见详版 §10.3 与 §12。

### 6.2 分层

```
Host       WPF 托盘 / 单实例 / 自启
```

### 6.4 线程与 COM

- UI 线程 STA。
- WASAPI 单独一个 MTA 线程，所有 COM 对象只在该线程创建与释放，**不要跨线程传接口指针**。
- SMTC 调用可异步；不要在 UI 线程阻塞等 `IAsyncOperation`。
- 会话对象要处理 `Expired`；设备变化时整体重建枚举器。

### 6.5 关键 API

| 用途 | API |
|---|---|
| 枚举音频会话 | `IMMDeviceEnumerator` → `IAudioSessionManager2` → `GetSessionEnumerator()` |
| 会话进程 | `IAudioSessionControl2::GetProcessId` |
| 会话状态 | `IAudioSessionControl::GetState()`（Active/Inactive/Expired） |
| 实时峰值 | `IAudioMeterInformation::GetPeakValue()`（需 QueryInterface） |
| 系统主音量 | `IAudioEndpointVolume`（`Get/SetMasterVolumeLevelScalar`） |
| 会话音量/静音 | `ISimpleAudioVolume`（本版不用其静音） |
| 媒体会话 | `GlobalSystemMediaTransportControlsSessionManager.RequestAsync()` |
| 播放状态 | `PlaybackStatus`：Closed=0, Opened=1, Changing=2, Stopped=3, Playing=4, Paused=5 |
| 定向暂停 | `session.TryPauseAsync()` / `TryPlayAsync()` |
| 模拟热键 | `SendInput`（用扫描码，避免输入法/布局影响） |

### 6.6 实现注意

1. **NAudio 不保证封装了 per-session 的 `IAudioMeterInformation`**，很可能需要自己写一小段 interop（推荐 `Microsoft.Windows.CsWin32` 生成，或手写 ComImport）。先验证，再决定是否全用 NAudio。
2. **exe 名匹配，不要用完整路径**。QQ 音乐装在 `...\QQMusic2271.07.38.24\QQMusic.exe`，升级即变。
3. **单实例 Mutex**：正式版 `Local\AutoVolume`，开发版加 `-dev` 后缀。
4. **配置原子写**：临时文件 → `File.Replace`。
5. **热键发送**：`SendInput` 后 300 ms 查会话状态；失败停止重试，防 toggle 反转。
6. **提权目标**：普通权限发键会被 UIPI 拦，检测到就标记"不可控"。
7. **多实例播放器**：热键可能被多个实例响应，禁用该播放器热键路径并提示。
8. **不要开 PublishTrimmed**：WPF 不支持，运行时会炸。
